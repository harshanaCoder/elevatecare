# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install                              # install dependencies
cp .env.example .env                     # then fill in DB_PASSWORD, SESSION_SECRET, ADMIN_PASSWORD_HASH
node scripts/hash-password.js "Pass123"  # generates a bcrypt hash to paste into .env (see Auth below)
npm run dev                              # nodemon, auto-restarts on file changes (predev hook rebuilds Tailwind CSS first)
npm start                                # plain node, no restart-on-change (prestart hook rebuilds Tailwind CSS first)
npm run build:css                        # manually rebuild public/css/tailwind.css after adding new Tailwind classes
npm run watch:css                        # rebuild Tailwind CSS on every save — run alongside `npm run dev` if iterating on markup a lot

docker compose up -d --build             # rebuild + run app + db + caddy (same compose file locally and on a cloud VM; Dockerfile's build stage runs `npm run build:css` itself)
docker compose logs app                  # check startup / DB connection logs
docker compose down                      # stop (add -v to also wipe the db_data volume)

./db/backup.sh                           # dump the live DB to backups/*.sql.gz (gitignored)
./db/restore.sh backups/<file>.sql.gz    # replace current data with a backup (asks for confirmation)
```

There is no test suite (`npm test` is a placeholder) and no lint/formatter configured. Verify changes by running the dev server and exercising the affected page or `/api/*` endpoint directly (curl or the browser).

**Schema changes have no migration framework.** `db/init.sql` only runs automatically the *first* time the Docker `db` volume is created. Any schema change also needs a corresponding one-off `db/add_*.sql` file (see `add_indexes.sql`, `add_technicians_table.sql`) that gets applied manually to already-provisioned databases:
```bash
mysql -u root -p elevatecare_db < db/add_something.sql
# or, against the Docker db container:
docker compose exec -T db mysql -uroot -p"$DB_PASSWORD" elevatecare_db < db/add_something.sql
```

## Architecture

**Stack:** Express 5 + `mysql2` (raw SQL via a connection pool, no ORM) on the backend. Static HTML + Tailwind + vanilla JS on the frontend — no bundler, no frontend framework. A single Express process ([src/server.js](src/server.js)) serves both `/api/*` and the static files in `public/` from the same origin, which is why `public/js/config.js` hardcodes `API_BASE = '/api'`.

**Tailwind is compiled, not loaded from its CDN Play script** (that CDN build ships the whole JIT compiler to the browser and recompiles on every page load — fine for prototyping, explicitly not for production, per Tailwind's own docs). [tailwind.config.js](tailwind.config.js) has `content: ['./public/**/*.html', './public/**/*.js']` — both, because `sidebar.js`/`footer.js` build their markup (including Tailwind classes) at runtime, not just the `.html` files — and `darkMode: 'class'`. `npm run build:css` compiles [src/styles/tailwind-input.css](src/styles/tailwind-input.css) into `public/css/tailwind.css`, which is gitignored (a build artifact, not source) and regenerated by `prestart`/`predev` npm hooks locally and by the `build` stage of the Dockerfile in Docker. `npm run watch:css` rebuilds on save if you're iterating on markup a lot — there's no other "just refresh and see it" path anymore now that the CDN's client-side JIT is gone.

**Auth is session-based with no user table and no server-side session store.** `cookie-session` backs a fixed set of role/username/password-hash triples read straight from `.env` ([src/routes/auth.routes.js](src/routes/auth.routes.js) `loadAccounts()`). Password hashes are stored **base64-encoded**, not raw bcrypt, because Docker Compose interpolates `$...$` sequences in `.env` values and would corrupt a raw hash — `scripts/hash-password.js` produces the base64 form directly.

The session (`role`, `username`) is stored entirely inside a signed cookie — there's nothing server-side to invalidate, so a server restart (nodemon reload, Docker rebuild, crash) no longer logs everyone out (it used to, back when this was `express-session`'s default in-memory store; briefly went through a MySQL-backed store too before landing here — cookie-only is simplest for an app with just two fixed accounts and no per-session revocation need). Logging out is `req.session = null`, not `.destroy()` — that's a `cookie-session` API difference from `express-session`, easy to get wrong if copying patterns from elsewhere. Rotating `SESSION_SECRET` invalidates every session at once; there's no way to revoke just one.

**Authorization is centralized, not per-route.** A single middleware in `server.js` gates every request before it reaches static files or `/api/*`: `PUBLIC_PATHS` lists what needs no session, `ROLE_ACCESS` is an allowlist keyed by role naming exactly which pages/API paths a non-admin role may hit (`admin` always passes everything). Adding a role means adding one entry there. `public/js/sidebar.js`'s `ROLE_VISIBLE_PAGES` must be kept in sync manually — it only controls which nav links are *shown*, the actual enforcement is server-side.

**Routing:** one router file per resource under `src/routes/*.js` (`breakdowns`, `services`, `unitSpecs`, `pending`, `auth`, `technicians`), each mounted at `/api` in `server.js`. Routes query MySQL directly through the shared pool in [src/config/db.js](src/config/db.js) using callback-style `db.query`. The one exception is `pending.routes.js`'s approve endpoint, which uses a manual transaction (`db.getConnection` + `beginTransaction`/`commit`/`rollback`) because approving a pending breakdown has to insert into `breakdowns` and delete from `pending_breakdowns` atomically.

**Frontend pages are independent HTML files** under `public/`, each with its own inline `<script>` that fetches from `API_BASE`, filters/maps the JSON client-side, and renders it via template-string `innerHTML` (see `public/technicians.html` or `public/services.html` for the pattern). There's no shared frontend state or framework — `public/js/sidebar.js` and `public/js/footer.js` are the shared pieces, each self-rendering into the page (`#sidebar-root` / appended to `<body>`) the same way. `public/js/sidebar.js` also re-checks `/api/auth/me` to trim the nav for non-admin roles.

**Dark/light mode** is Tailwind's class-based strategy (`darkMode: 'class'` in `tailwind.config.js`, baked into `public/css/tailwind.css` at build time — no per-page runtime config needed now that Tailwind isn't the CDN script). Every page still has a tiny *inline* (not external — must run before the stylesheet's rules would otherwise apply the wrong theme, so it can't wait on a network request) script in `<head>` that reads `localStorage.theme` and adds the `dark` class to `<html>` before first paint, avoiding a flash of the wrong theme. `public/js/theme.js` holds the actual toggle logic (`window.ElevateTheme.getTheme/applyTheme/toggleTheme`) — [public/settings.html](public/settings.html) is the only page with a UI control for it. Since most `<input>`/`<select>`/`<textarea>` elements across the app have no explicit `bg-*`/`text-*` classes (they rely on the browser's white default), annotating every one individually with `dark:` utilities wasn't practical — [public/css/theme.css](public/css/theme.css) instead has a small `html.dark input, select, textarea {...}` catch-all covering all of them at once, loaded on every page alongside `tailwind.css`. `/css/` had to be added to `server.js`'s `isPublicPath()` allowlist (alongside the existing `/js/` one) so both stylesheets load on the pre-login `login.html` too. Not every element got hand-tuned `dark:` variants (small colored status badges/chips were left as-is — they stay readable as light chips on a dark background, a common enough pattern) — if a specific spot looks off in dark mode, it's a targeted one-line fix, not a sign the mechanism is broken.

**A new Tailwind class added to any page's markup needs a CSS rebuild to actually appear** (`npm run build:css`, or restart `npm run dev` — see Commands). Unlike the old CDN Play script, there's no client-side JIT anymore quietly compiling whatever class names it finds at request time — a class that's typo'd or simply never gets rebuilt will silently do nothing, same as any other unrecognized CSS class.

**The footer** ([public/js/footer.js](public/js/footer.js)) is `position: fixed` at the bottom of the viewport rather than part of each page's own flex/scroll layout — this was deliberate: pages have meaningfully different internal layouts (compare `lifts.html`'s nested flex-col/overflow-hidden structure to the flat `flex-1 overflow-y-auto` used elsewhere), and injecting a real DOM node at the *end* of "the content area" would have needed page-by-page layout awareness with real risk of being clipped by an `overflow-hidden` ancestor. A fixed bar sidesteps all of that at the cost of needing bottom padding (`pb-12` or similar) on each page's scrollable area so content doesn't scroll under it.

**Deployment** ([docker-compose.yml](docker-compose.yml)) runs three services: `app` (this repo), `db` (`mysql:8.4`, refuses to start with an empty `DB_PASSWORD` on purpose), and `caddy` (reverse proxy + automatic HTTPS via `Caddyfile`). The same compose file is meant to run unchanged on a local machine or a cloud VM.

**Comment style:** some route files (`pending.routes.js`, `unitSpecs.routes.js`) mix romanized Sinhala into comments — that's intentional from the original author, not something to translate or "fix" in passing.

## UI conventions for add/edit/delete forms

These apply to any page with a create/update/delete flow (e.g. `technicians.html`):

- Success and error messages are toasts: fixed to the bottom of the screen, colored by type (green success / red error), auto-dismiss after ~3 seconds. Don't render them inline in a modal or form.
- Adding a record → show a success toast. Updating a record → show a success toast.
- Deleting a record always requires a confirmation dialog first — never delete on a single click.
- Error messages use one consistent fallback string across add/update/delete (not a different "Unknown error" wording per action).
- Don't change existing functionality while implementing these unless it's specifically requested.
