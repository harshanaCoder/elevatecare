# ElevateCare

Internal operations dashboard for managing elevator/escalator breakdowns,
maintenance services, spare parts, and technicians.

## Stack

- **Backend:** Node.js + Express 5 + MySQL (`mysql2`)
- **Frontend:** Static HTML + Tailwind CSS + vanilla JS — no frontend framework, no bundler. Tailwind itself is compiled ahead of time (`npm run build:css`) rather than loaded from its CDN Play script — that CDN build ships the whole JIT compiler to the browser and recompiles on every page load, which Tailwind's own docs say is for prototyping, not production.

## Project structure

```
public/            # Frontend — served statically by Express
  *.html           # One page per section (dashboard, breakdowns, services, ...)
  js/
    config.js      # window.API_BASE — where the frontend calls the API
    sidebar.js      # Shared nav, rendered into <div id="sidebar-root"> on every page
    footer.js       # Shared footer, appended to <body> the same way
    theme.js        # Light/dark toggle logic (localStorage-backed), used by settings.html
  css/
    tailwind.css    # Generated by `npm run build:css` — gitignored, not hand-edited
    theme.css       # Hand-written dark-mode overrides for form fields (inputs/selects/textareas)
src/                # Backend
  server.js         # App entry point: static hosting + session/auth gate + API routes
  config/db.js      # MySQL connection pool (reads from .env)
  routes/           # One router per resource (auth, breakdowns, services, unit specs, pending, technicians)
  styles/
    tailwind-input.css  # Source file for the Tailwind build (@tailwind base/components/utilities)
scripts/
  hash-password.js  # Generates the bcrypt hash for ADMIN_PASSWORD_HASH
tailwind.config.js   # content globs + darkMode: 'class' for the Tailwind build
```

## Setup

1. Install dependencies:
   ```
   npm install
   ```
2. Copy the env template and fill in your local DB credentials:
   ```
   cp .env.example .env
   ```
3. Make sure MySQL is running locally with an `elevatecare_db` database
   matching the schema used by `src/routes/*.js` (breakdowns, services,
   unit_specifications, pending_breakdowns tables). If that database
   predates this repo's `db/init.sql`, run `db/add_indexes.sql` against it
   once (`mysql -u root -p elevatecare_db < db/add_indexes.sql`) — every
   page filters/sorts by `unit_no`, a date column, or a status column, and
   those weren't indexed before.
4. Run the app:
   ```
   npm run dev    # auto-restarts on file changes (nodemon)
   # or
   npm start
   ```
   Both commands compile Tailwind's CSS first (a `predev`/`prestart` npm
   hook runs `npm run build:css` automatically) — you don't need to run it
   yourself for a normal `npm run dev` / `npm start`. You only need to
   re-run `npm run build:css` manually (or restart `npm run dev`) if you add
   a new Tailwind class to a page and want to see it without a full restart;
   `npm run watch:css` rebuilds on every save if you're doing that a lot.
5. Open http://localhost:5000 — it redirects to the dashboard. The same
   Express server serves both the frontend and the `/api/*` routes.

## Environment variables

See `.env.example`: `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `PORT`,
plus `ADMIN_USERNAME` / `ADMIN_PASSWORD_HASH` / `SESSION_SECRET` (see Login
below). `.env` is gitignored — never commit real credentials.

## Login

No user table — accounts are configured in `.env`, one username/password
pair per role. Every page and every `/api/*` route redirects to
`/login.html` (or returns `401`/`403`) until you're signed in as a role
that's allowed there.

- **`admin`** — full access to everything.
- **`reports`** (optional) — restricted to `reports.html` and the two
  read-only endpoints it calls (`/api/all-breakdowns`,
  `/api/breakdowns-filter`). Everything else 403s for API calls and
  redirects back to `reports.html` for pages. This is enforced in
  `ROLE_ACCESS` in `src/server.js` — add another role there (and a matching
  block in `public/js/sidebar.js`'s `ROLE_VISIBLE_PAGES`, so the sidebar
  hides links that role can't use) following the same pattern. Leave
  `REPORTS_USERNAME`/`REPORTS_PASSWORD_HASH` blank in `.env` to disable it.

For either role:
- Set the password once:
  ```
  node scripts/hash-password.js "YourNewPassword"
  ```
  Paste the printed hash into `.env` (`ADMIN_PASSWORD_HASH` or
  `REPORTS_PASSWORD_HASH`) and set the matching `*_USERNAME`. The real
  password is never stored anywhere — only this hash.
- `SESSION_SECRET` signs the login cookie — any long random string works
  (`.env.example` shows how to generate one).
- Sessions last 8 hours and live entirely inside a signed cookie
  (`cookie-session` — no server-side session store), so restarting the
  server — `nodemon` reloading, a Docker rebuild, a crash — no longer logs
  everyone out. Only an expired (8h) session or an explicit logout does.
  Rotating `SESSION_SECRET` invalidates every session at once (there's no
  way to revoke just one).
- Logout is the button at the bottom of the sidebar on every page.

## Running with Docker (local or on a cloud VM)

The same `docker-compose.yml` works identically on your machine and on any
cloud VM (Oracle Cloud, AWS, etc.) — it's what you'll actually deploy with,
and it's the setup this app is meant to run in for anything beyond your own
laptop.

```
db/init.sql          # creates the schema on a fresh DB container only
Dockerfile            # builds the app image (two stages — see below)
docker-compose.yml    # app + MySQL + Caddy (reverse proxy / HTTPS)
Caddyfile              # reverse proxy config
```

### Quick start

1. In `.env`, set a **real, non-empty `DB_PASSWORD`** — the `db` service
   refuses to start with a blank one on purpose (fine for `npm run dev`
   against your existing local MySQL, not fine for Docker/production).
2. `docker compose up -d --build`
3. Open http://localhost — Caddy proxies everything to the app container.
4. `docker compose logs app` to check startup / DB connection logs.
5. `docker compose down` to stop (add `-v` to also wipe the DB volume —
   don't do that once there's real data in it).

That's the whole workflow — steps 1–5 haven't changed. What changed is
what `docker compose up -d --build` does internally (below), not how you
invoke it.

### How the app image is built (two stages)

The `Dockerfile` builds the `app` image in two stages so the final image
that actually runs doesn't carry any build tooling:

1. **`build` stage** — installs *all* dependencies (including
   `devDependencies`, notably `tailwindcss`) and runs `npm run build:css`,
   which compiles `src/styles/tailwind-input.css` + every class actually
   used across `public/**/*.html` and `public/**/*.js` into a single
   minified `public/css/tailwind.css`. This is the production replacement
   for the Tailwind CDN script used in some earlier setups — the CDN Play
   build ships the whole JIT compiler to the browser and recompiles on
   every page load, which is fine for prototyping but not for a real
   deployment.
2. **runtime stage** — a fresh image with only `npm ci --omit=dev` (no
   `tailwindcss`, no build tooling), copying `public/` *from the build
   stage* (so it already has the compiled CSS baked in) rather than from
   your working directory.

You don't need to run `npm run build:css` yourself before `docker compose
up --build` — the build stage does it automatically, from whatever's
currently in `public/` and `src/` at build time. If you change a page's
markup and add new Tailwind classes, just rebuild
(`docker compose up -d --build`) and the new classes will be picked up;
there's nothing to purge/allowlist manually.

`public/css/tailwind.css` itself is gitignored — it's a build artifact,
regenerated fresh on every `docker compose up --build` and by
`npm start`/`npm run dev` locally (via `prestart`/`predev` hooks). Don't
hand-edit it or expect it to exist right after a fresh `git clone` without
running one of those.

**Deploying to a cloud VM:** install Docker + Docker Compose on the VM, copy
this repo over (git, or `scp`), create a `.env` there with real values, then
run the same `docker compose up -d --build`. Once you have a domain pointed
at the VM's IP, edit `Caddyfile` to use it (see the comment inside) and Caddy
will fetch a free HTTPS certificate automatically — no manual Certbot setup.

**Note on `db/init.sql`:** it was reconstructed from the columns
`src/routes/*.js` actually queries, since no schema file existed in the repo.
It only runs once, the first time the `db` volume is created — it never
touches your existing local database. Before relying on it for a real
deployment, compare it against your actual local schema (or replace it with
`mysqldump -u root -p --no-data elevatecare_db > db/init.sql`).

### Backups

The `db` container's data lives in a Docker volume (`db_data`) — that
survives restarts and redeploys, but not a lost VM disk or a stray
`docker compose down -v`. There's no other backup happening on its own.

- **Back up:** `./db/backup.sh` — dumps the live database to
  `backups/elevatecare_<timestamp>.sql.gz` (gitignored; these contain real
  data). Keeps the most recent 14 automatically.
- **Restore:** `./db/restore.sh backups/elevatecare_<timestamp>.sql.gz` —
  asks for confirmation, then replaces all current data with that backup.
- **On the actual server**, schedule the backup with cron so it's not
  something you have to remember:
  ```
  crontab -e
  # add a line like:
  0 2 * * * cd /path/to/ElevateCare && ./db/backup.sh >> /var/log/elevatecare-backup.log 2>&1
  ```
  That runs it daily at 2am. For anything beyond "the VM's own disk," copy
  the `backups/` folder somewhere else too (e.g. a small script that syncs
  it to Oracle Object Storage / AWS S3) — a backup that lives on the same
  disk as the database it's backing up doesn't protect against disk failure.

### A note if you're considering AWS's free tier for this

AWS's free-tier EC2 instance (t2/t3.micro) has **1GB of RAM total** — MySQL,
Node, and Caddy all running there at once is tight, and MySQL is the biggest
consumer. It'll likely work for light use, but has little headroom. Oracle
Cloud's Always Free ARM VM (4 OCPU / 24GB RAM) doesn't have this problem,
which is the main reason it's the one recommended earlier.
